# Концепт метрик объёма работы

## Что показываем

Основной временной интервал — календарный месяц. Выполненной работой считаем
merge request, который был влит в этом месяце (`merged_at`), а не просто создан.

Для команды и каждого сотрудника показываем:

- количество влитых MR;
- добавленные строки;
- удалённые строки;
- всего изменённых строк (`added + deleted`);
- количество изменённых файлов;
- медиану изменённых строк на MR;
- динамику относительно предыдущего сопоставимого периода;
- персональный сигнал относительно собственной исторической медианы.

Один общий блок фильтров используется вкладками «Статистика» и «Динамика».
Команды берём из `data/routes.json`. После выбора команды список сотрудников
строится из её `members`; значение «Все сотрудники» агрегирует участников.
Поддерживаем пресеты: 1 и 2 недели, текущий и прошлый месяц, текущий и прошлый
квартал, полгода, год и произвольный диапазон дат. Даты показываем только для
произвольного диапазона. Отдельную подпись выбранного периода под фильтрами не
дублируем.

Подписи временных интервалов компактные и однозначные: месяц — `07'26`,
квартал — `2q'26`, неделя — `34w'26`.

Шаг графика зависит от выбранного периода:

- неделя, две недели, текущий и прошлый месяц — один столбец на календарный день;
- квартал и полгода — один столбец на месяц;
- год — месяцы, а при расширении диапазона свыше года — кварталы;
- произвольный диапазон выбирает шаг автоматически по своей длине.

Основная динамика отображается линейными диаграммами. Количество влитых MR —
отдельная линия с лёгкой заливкой области. Добавленные и удалённые строки — две
линии на левой шкале, количество изменённых файлов — третья линия на отдельной
правой шкале. Точное значение точки показывается при наведении.

Строки кода и количество MR — показатели объёма изменений, а не качества или
продуктивности. Они не должны использоваться для рейтинга сотрудников.

## Источник данных

1. Получаем MR для настроенных групп и проектов.
2. Оставляем влитые MR и относим их к месяцу по `merged_at`.
3. Основной источник — GitLab GraphQL `diffStatsSummary`: берём готовые
   `additions`, `deletions`, `changes` и `fileCount`.
4. Если установленная версия GitLab не поддерживает эти GraphQL-поля,
   переключаемся на `GET /projects/:id/merge_requests/:iid/diffs` с пагинацией.
5. В резервном режиме считаем строки unified diff:
   - строка с `+`, кроме заголовка `+++`, считается добавленной;
   - строка с `-`, кроме заголовка `---`, считается удалённой;
   - контекстные строки не считаются;
   - файлы с `generated_file=true` по умолчанию исключаются.
6. Если GitLab возвращает `collapsed` или `too_large`, помечаем MR как
   посчитанный не полностью и показываем это в интерфейсе.

Endpoint `/changes` использовать не нужно: он устарел. Endpoint `/diffs`
поддерживает пагинацию, но всё равно подчиняется серверным ограничениям diff.

### ADR: получение статистики строк MR

**Решение:** готовые агрегаты GitLab GraphQL являются основным источником.
Разбор REST diff используется только как резервный совместимый механизм.

Основной запрос отправляется в `/api/graphql`:

```graphql
query MergeRequestDiffStats($project: ID!, $iid: String!) {
  project(fullPath: $project) {
    mergeRequest(iid: $iid) {
      diffStatsSummary {
        additions
        deletions
        changes
        fileCount
      }
    }
  }
}
```

Значения трактуются так:

- `additions` — добавленные строки;
- `deletions` — удалённые строки;
- `changes` — общий объём изменений;
- `fileCount` — количество изменённых файлов.

При запуске клиент один раз проверяет поддержку `diffStatsSummary` безопасным
тестовым запросом. Результат capability-проверки сохраняется для адреса и версии
GitLab. Ошибки авторизации, сети и rate limit не считаются отсутствием функции и
не должны навсегда переключать приложение на fallback.

Порядок выбора источника:

1. `GraphQLDiffStatsProvider` — основной путь для всего MR.
2. `RepositoryDiffStatsProvider` — опциональная оптимизация для GitLab 19.4+,
   только если beta endpoint `/repository/diff_stats` реально доступен.
3. `ParsedDiffStatsProvider` — пагинирует MR `/diffs` и считает unified diff.

REST `changes_count` не используется: это не количество строк, значение
заполняется асинхронно и ограничивается строкой `1000+`. Статистика отдельных
коммитов (`stats.additions`, `stats.deletions`, `stats.total`) также не
суммируется: повторные правки и откаты внутри MR приведут к двойному подсчёту и
не будут равны итоговой разнице MR.

GraphQL `diffStatsSummary` включает все файлы. Если появится продуктовая
настройка исключать lock-файлы, сгенерированные файлы или отдельные пути,
используем построчный `diffStats` либо `ParsedDiffStatsProvider`. В ответе API
обязательно сохраняем происхождение и полноту результата.

```go
type DiffStats struct {
    Additions  int
    Deletions  int
    Changes   int
    FileCount int
    Complete  bool
    Source    string
}

type MRDiffStatsProvider interface {
    Stats(ctx context.Context, projectPath string, iid int) (DiffStats, error)
}

type FallbackDiffStatsProvider struct {
    primary  MRDiffStatsProvider
    fallback MRDiffStatsProvider
}
```

Fallback выполняется только при типизированной ошибке `ErrNotSupported` или
при неполном ответе, для которого резервный источник способен дать более
полные данные. Обычная ошибка GitLab возвращается вызывающему коду и проходит
стандартную retry-политику. Благодаря этому временный `403`, `429` или timeout
не маскируется дорогостоящим разбором всех diff.

## Локальное хранение

Для динамики нужен постоянный локальный кэш: пересчитывать diff всех MR за
полгода при каждом открытии слишком долго.

Предлагаемая база — один локальный SQLite-файл `data/pulse-review.db`:

```text
merge_requests
  project_id, iid, author_id, author_username
  created_at, merged_at, updated_at, state
  additions, deletions, changed_lines, changed_files
  diff_source, diff_complete, generated_files_excluded
  collected_at

monthly_person_metrics
  month, team_id, user_id
  merged_mrs, additions, deletions, changed_lines
  incomplete_mrs
```

Ключ MR — `(project_id, iid)`. Пока MR открыт, данные обновляются при изменении
`updated_at`. После merge итоговый diff сохраняется; повторный запрос нужен
только при ручном полном обновлении.

SQLite должен подключаться через pure-Go драйвер без CGO, чтобы сохранить одну
и ту же сборку для Windows, Mac Apple Silicon и Mac Intel.

## Компоненты backend

```text
GitLab collector
  -> MR normalizer
  -> diff counter
  -> local SQLite store
  -> monthly aggregator
  -> /api/work-volume
  -> вкладка «Динамика»
```

- `collector` ограничивает параллелизм и повторяет запросы при временных
  ошибках/ограничении частоты GitLab;
- `diff counter` отвечает только за корректный подсчёт unified diff;
- `store` делает запись идемпотентной и не допускает двойного подсчёта MR,
  попавшего одновременно через группу и проект;
- `aggregator` строит общий, командный и персональный месячные ряды;
- API возвращает также `incompleteMRs`, чтобы интерфейс показывал качество
  данных.

Правила расчёта не должны находиться в HTTP-обработчиках, хранилище или
компонентах интерфейса. В Go они задаются небольшими интерфейсами и передаются
сервису аналитики как зависимости:

```go
type VolumePolicy interface {
    ChangedLines(additions, deletions int) int
    Median(values []int) int
}

type SignalPolicy interface {
    Evaluate(current, baseline Sample) Signal
}

type AnalyticsService struct {
    repository        MergeRequestRepository
    diffStatsProvider MRDiffStatsProvider
    volumePolicy      VolumePolicy
    signalPolicy      SignalPolicy
}
```

Это позволяет заменить способ подсчёта строк, медианы или сигнала, не меняя
GitLab-клиент, API и отображение. Стандартная реализация покрывается табличными
unit-тестами; альтернативная передаётся через конструктор.

Обязательные тесты провайдеров:

- успешный GraphQL-ответ со всеми четырьмя числами;
- `null` и отсутствие поля на старой версии GitLab;
- GraphQL errors при `403`, `429` и временной ошибке;
- переключение на fallback только для `ErrNotSupported`;
- пагинация REST `/diffs`;
- корректный подсчёт `+`/`-` без служебных `+++`/`---`;
- new/delete/rename/binary/generated/collapsed/too-large файлы;
- совпадение GraphQL и fallback на одной контрольной выборке MR;
- отсутствие двойного подсчёта MR, найденного через несколько источников.

Для процента к предыдущему периоду сервис расширяет запрашиваемый диапазон назад
на такую же длительность. Например, при выборе последних 30 дней он получает и
предыдущие 30 дней, затем сохраняет оба диапазона в локальный кэш. Если GitLab не
вернул полный предыдущий диапазон, API не отдаёт сравнение, а интерфейс скрывает
процент вместо расчёта по неполным данным.

Пример API:

```http
GET /api/work-volume?from=2026-02&to=2026-07&team=all&username=
```

```json
{
  "scope": { "team": "all", "username": null },
  "months": [
    {
      "month": "2026-07",
      "mergedMRs": 34,
      "additions": 8420,
      "deletions": 3180,
      "changedLines": 11600,
      "changedFiles": 47,
      "medianChangedLinesPerMR": 276,
      "incompleteMRs": 1
    }
  ]
}
```

## Интерпретация динамики

Для внедрения AI в настройках можно хранить дату начала эксперимента и
сравнивать медиану 3–6 месяцев до и после неё. Интерфейс должен писать
«объём изменений вырос», а не «AI повысил продуктивность»: на результат также
влияют тип задач, отпуска, состав команды и крупные рефакторинги.

Медиану не требуется хранить как готовое число. Для каждого влитого MR уже
сохранены `additions` и `deletions`; сервис строит выборку размеров MR и считает
медиану при агрегации. Кэшировать можно исходные MR и месячные агрегаты, но не
само правило вычисления.

«В пределах нормы» означает, что средний размер MR за выбранный период
отклоняется от личной медианы базового периода не больше настроенного порога.
Стандартный порог — `±20%`, минимальная выборка — 5 влитых MR. Порог является
параметром `SignalPolicy` и редактируется в разделе «Настройки аналитики» вместе
с минимальным размером выборки. Настройка сохраняется локально.
При недостатке данных показываем «Недостаточно данных», а не норму. При выходе
за порог формулировка — «Посмотреть контекст». Система не диагностирует
выгорание и не делает выводов о качестве работы человека.

## Этапы реализации

1. Согласовать концепт интерфейса и определения метрик.
2. Добавить подсчёт diff и тесты на добавление, удаление, rename, binary,
   generated, collapsed и too-large файлы.
3. Добавить SQLite-кэш и миграции схемы.
4. Реализовать сбор и API месячной динамики.
5. Подключить вкладку к реальным данным и показать полноту выборки.
6. Проверить на небольшом и большом приватном проекте, затем прогнать CI на
   Windows и macOS.
