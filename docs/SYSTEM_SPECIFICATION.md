# Pulse Review — системная спецификация

Статус: живой документ, описывает фактическую Go-реализацию и обязательные
архитектурные границы. Версия приложения на момент создания документа: `0.2.1`.

Этот файл предназначен одновременно для разработчиков и ИИ-агентов. Его задача —
позволить восстановить контекст решения без чтения всей истории обсуждений.

## 1. Как пользоваться документацией

При расхождении источников действует следующий приоритет:

1. подтверждённые требования в [PRODUCT_REQUIREMENTS.md](PRODUCT_REQUIREMENTS.md);
2. контракты и инварианты из этой спецификации;
3. автоматические тесты;
4. фактический код;
5. README, макеты и история переписки.

Если код расходится с требованиями, нельзя молча объявлять код новым стандартом.
Нужно определить, является ли расхождение дефектом или новым продуктовым решением,
обновить документацию и добавить регрессионный тест.

### Быстрое восстановление контекста для ИИ

Перед любой доработкой:

1. прочитать `docs/PRODUCT_REQUIREMENTS.md` и этот файл полностью;
2. посмотреть `git status --short` и не затрагивать чужие незакоммиченные файлы;
3. посмотреть последние коммиты: `git log --oneline -10`;
4. найти затрагиваемый контракт через `rg` в коде и тестах;
5. установить, меняется продуктовый смысл, API, расчёт или только представление;
6. после изменения выполнить проверки из раздела 14;
7. обновить спецификацию, если изменился контракт или инвариант.

Нельзя восстанавливать требования только по `public/index.html`: интерфейс содержит
как production-поведение, так и демонстрационные данные для автономного просмотра.

## 2. Назначение и границы продукта

Pulse Review — локальное self-hosted приложение для руководителя команды. Оно:

- получает данные из одного GitLab-сервера;
- агрегирует review-активность и объём изменений по настроенным командам;
- показывает общие показатели, динамику и расшифровку по сотрудникам;
- хранит подключение и конфигурацию только на компьютере пользователя;
- распространяется как самостоятельный Go-бинарник для macOS и Windows.

Приложение не является системой оценки производительности, не диагностирует
выгорание и не доказывает влияние ИИ. Строки, файлы и MR — показатели объёма
изменений, которые требуют контекста задач.

### Не входит в текущий объём

- облачный сервер и общий аккаунт организации;
- синхронизация настроек между компьютерами;
- Linux как пользовательская release-платформа;
- альтернативный runtime помимо Go-бинарника;
- постоянная база исторических MR;
- автоматический вывод о качестве, эффективности или выгорании сотрудника.

## 3. Текущее состояние и целевое направление

### Реализовано сейчас

- один Go-процесс: HTTP API и встроенная статика;
- интерфейс без frontend-фреймворка в `public/index.html`;
- локальные JSON-файлы конфигурации в `data/`;
- GitLab REST для review-отчёта;
- GitLab GraphQL `diffStatsSummary` с REST `/diffs` fallback для объёма;
- агрегация объёма в памяти на каждый запрос;
- атомарный дневной ряд объёма на общем, командном и персональном уровнях;
- кэши отчётов и объёма в памяти процесса;
- вкладки «Дашборд», «Ревью», «Динамика», «Настройки»;
- CI на macOS и Windows.

### Целевое направление, ещё не реализовано полностью

- разделение большого frontend-файла на модули по ответственности;
- выделенный application/service слой для обоих видов аналитики;
- постоянный pure-Go SQLite-кэш нормализованных MR и diff-статистики;
- типизированные ошибки GitLab и fallback только по `ErrNotSupported`;
- ADR для каждого изменения формулы, хранения или внешнего контракта.

Документ [WORK_VOLUME_ARCHITECTURE.md](WORK_VOLUME_ARCHITECTURE.md) содержит
детальный проект целевого хранилища и заменяемых политик. Его предложения нельзя
считать уже реализованными без проверки кода.

## 4. Архитектурная схема

```text
Browser (одна HTML-страница)
  ├─ общие фильтры и состояние вкладок
  ├─ Review UI ─────────────── GET /api/report
  ├─ Dashboard / Dynamics ──── GET /api/work-volume
  └─ Settings ──────────────── GET/POST /api/config, /api/connection
                                   │
Go application                     │
  ├─ HTTP handlers                 │
  ├─ review collector/aggregator ──┤
  ├─ work-volume collector ────────┤
  ├─ diff stats providers          │
  ├─ in-memory caches              │
  └─ JSON configuration store      │
                                   ▼
                             GitLab REST/GraphQL
```

Поток зависимостей должен идти от HTTP и UI к предметной логике, а не наоборот.
GitLab-клиент не должен знать о DOM, текстах интерфейса или правилах визуализации.
Формулы не должны жить в HTTP-обработчиках.

### Известный долг frontend

`public/index.html` сейчас является монолитом. До его декомпозиции новые функции
должны хотя бы сохранять логические секции:

1. DOM-шаблон;
2. design tokens и стили компонентов;
3. API adapters;
4. domain transformations;
5. render functions;
6. event handlers;
7. bootstrapping.

Нельзя копировать расчёт одной метрики в несколько render-функций. Общая логика
графиков должна оставаться в `renderLineChart`, а группировка — в отдельных
чистых функциях.

## 6. Предметная модель

### Подключение

`connectionSettings`:

- `gitlabUrl` — origin GitLab без пути группы/проекта;
- `gitlabToken` — персональный token со scope `read_api`.

### Источник

Источник — нормализованный путь GitLab-группы или проекта. Один MR может быть
найден через несколько источников; уникальность определяется парой
`(project_id, iid)`.

### Команда (`route`)

- `id` — стабильный идентификатор в локальной конфигурации;
- `name` — отображаемое имя;
- `members` — GitLab usernames без `@`;
- `reviewSignal` — `approve`, `thumbsup` или их совместимый вариант;
- поля Mattermost существуют для обратной совместимости, но UI скрыт feature-флагом.

### Review-отчёт

Основная единица — сотрудник (`reviewer`) с approvals, комментариями, созданными
MR, полученными комментариями и открытыми MR. Отчёт содержит общий результат и
разрез `teams`.

### Объём изменений

`volumePoint` — один непересекающийся временной интервал:

- `period`, `label`;
- `mergedMRs`;
- `additions`, `deletions`;
- `changedLines`;
- `changedFiles`;
- `medianChangedLinesPerMR`;
- `incompleteMRs`.

`workVolumeResponse` содержит адаптивный `overall`, атомарный `daily`, команды,
сотрудников и число собранных MR. Командные и персональные ряды используют одну
схему точки и также содержат пару `series`/`daily`. `daily` всегда имеет по одной
точке на каждый календарный день включительного диапазона, в том числе явные
нулевые дни. Из него UI без потери точности строит недели, месяцы и кварталы.
Адаптивный `series` остаётся оптимизированным рядом для прямого показа.

Локально перегруппировываются только аддитивные показатели: `mergedMRs`,
`additions`, `deletions` и `changedFiles`. Медиану нельзя получать сложением или
усреднением медиан дневных точек; для неё нужен исходный набор размеров MR либо
отдельный серверный расчёт.

## 7. Формулы и семантика времени

### Review

- approval/👍: уникальная пара `ревьюер + MR` по правилу команды;
- самоаппрув и собственный 👍 не учитываются;
- комментарий: несистемный комментарий сотрудника в чужом MR;
- созданный MR относится к периоду по `created_at`;
- открытый MR — созданный в периоде и остающийся открытым;
- вовлечённость = approvals/👍 + комментарии + созданные MR.

### Объём

- учитывается только влитый MR;
- временная принадлежность определяется `merged_at`;
- `changedLines = additions + deletions` в стандартной `volumePolicy`;
- `changedFiles` берётся из diff-статистики GitLab;
- медиана считается по размерам отдельных MR, а не по агрегированным периодам;
- отсутствующие или неполные diff отмечаются, а не подменяются нулём молча.

Все даты API имеют формат `YYYY-MM-DD` и трактуются как включительные границы.
Для календарных расчётов границы нормализуются до полуночи. Временные интервалы
не пересекаются, а сумма интервалов равна итогу выбранного диапазона.
Атомарная принадлежность MR к дню определяется календарной датой `merged_at` в
UTC; `daily` сохраняет нулевые дни и обе границы диапазона.

Общий объём включает MR авторов, перечисленных хотя бы в одной настроенной
команде. Если существует команда с пустым списком участников, в общий объём и
в эту команду входят все авторы найденных MR. Один MR в общем ряду учитывается
один раз, даже если его автор состоит в нескольких командах.

### Серверная гранулярность `/api/work-volume`

| Длина диапазона | Точка API |
|---|---|
| до 31 дня включительно | день |
| 32–93 дня | последовательный семидневный интервал от `from` |
| больше 93 дней | календарный месяц |

### Группировки карточек Дашборда

| Общий период | Доступные виды |
|---|---|
| последняя неделя | дни |
| две недели | дни, недели |
| текущий/прошлый месяц | дни, недели |
| текущий/прошлый квартал | недели, месяцы |
| полгода, год | месяцы, кварталы |
| свои даты до 31 дня | дни, недели |
| свои даты от 32 до 93 дней | недели, месяцы |
| свои даты свыше 93 дней | месяцы, кварталы |

Группировка суммирует уже загруженные атомарные точки и не запускает GitLab
request. Нельзя строить более мелкий достоверный интервал из более крупного.
Для production-данных UI обязан использовать гранулярность ответа. Разложение
помесячных значений на недели допустимо только для явно демонстрационного набора
и не может попадать в ответы API или пользовательские выводы.

Интервал любой выбранной UI-группировки может быть скрыт локальной настройкой,
если все релевантные показатели в нём равны нулю. Настройка включена по
умолчанию, применяется к графикам Дашборда и Динамики и не изменяет атомарный
`daily` в API. При выключенной настройке нулевые дневные интервалы сохраняются.

## 8. Получение diff-статистики

Основной provider: GitLab GraphQL:

```graphql
diffStatsSummary { additions deletions changes fileCount }
```

Fallback: пагинируемый REST endpoint MR `/diffs` с разбором unified diff.

Правила fallback-подсчёта:

- `+`, кроме `+++`, увеличивает additions;
- `-`, кроме `---`, увеличивает deletions;
- контекст не учитывается;
- binary diff не создаёт фиктивные строки;
- collapsed/too-large делают результат неполным.

Текущая реализация переключается на fallback только при типизированной
`errDiffStatsNotSupported`. Временные `401/403/429/timeout` возвращаются как
ошибка. Следующее расширение — разрешить fallback для неполного ответа, когда
резервный provider способен вернуть более полные данные.

## 9. HTTP API

Все ответы JSON, кроме `/`, который отдаёт embedded static UI. Ошибка имеет
HTTP-статус и JSON с понятным пользователю полем ошибки.

### `GET /api/connection`

Возвращает URL и признак сохранённого token. Секрет не должен возвращаться UI.

### `POST /api/connection`

Проверяет URL/token запросом к GitLab и атомарно сохраняет подключение. Пустой
token означает «сохранить существующий», если он уже есть.

### `GET /api/config`

Возвращает `routes`, `groups`, `projects`, состояние GitLab и Mattermost.

### `POST /api/config`

Сохраняет команды и источники. Если передан объединённый `sources`, backend
классифицирует каждый путь как группу или проект через GitLab. После изменения
состава команд work-volume cache всегда очищается.

### `GET /api/report?from=YYYY-MM-DD&to=YYYY-MM-DD&team=ID|all&job=ID`

Строит Review-отчёт. `job` связывает запрос с `/api/progress`. Результат может
браться из 15-минутного memory cache.

### `GET /api/progress?id=ID`

Возвращает `phase`, `processed`, `total`, `cached`, `error`. Отмена основного
fetch должна отменять request context, а не только скрывать UI.

### `GET /api/work-volume?from=YYYY-MM-DD&to=YYYY-MM-DD`

Строит объём для всех настроенных команд. Фильтр команды применяется в UI к уже
полученному командному ответу. `overall`, `teams[].series` и
`teams[].people[].series` формируются по таблице адаптивной гранулярности из
раздела 7. Поля `daily`, `teams[].daily` и `teams[].people[].daily` содержат по
одной точке на каждый день включительного диапазона независимо от его длины.

### `POST /api/send`

Отправляет Review-отчёт в Mattermost при наличии webhook и включённого route.
Функция не должна быть видна в публичном UI без feature-флага.

## 10. Состояние интерфейса

### Глобальное

- активная вкладка;
- команда;
- пресет периода и границы своих дат;
- текущая загрузка и возможность отмены.

Команда и период общие для «Дашборда», «Ревью» и «Динамики». В «Настройках»
плашка фильтров скрыта. Период по умолчанию — последняя неделя.

### Локальное, без сетевого запроса

- включённые показатели легенды;
- включённые показатели легенды «Вовлечённости»;
- отображение или скрытие дневных интервалов без активности;
- представление карточек «График»/«Линейчатая»;
- группировка каждой карточки;
- сортировка таблицы;
- локальный отбор сотрудника по ФИО в таблице «Динамики»;
- закреплённый tooltip;
- полноэкранный график.

Изменение локального состояния не должно вызывать `/api/report` или
`/api/work-volume`.

### UI-инварианты

- существующая вкладка «Ревью» не меняет смысл расчётов при развитии Дашборда;
- заголовок вкладки — только «Ревью», без дублирующей подписи выбранного периода;
- клик по ФИО в таблице «Динамики» применяет локальный отбор сотрудника, повторный
  клик снимает его; отдельного общего поля сотрудника и отдельной плашки отбора нет;
- одинаковая сущность имеет одинаковую легенду, цвет и подпись во всех графиках;
- цвета: MR — фиолетовый, additions — синий, deletions — оранжевый,
  files — зелёный;
- легенда кликабельна, скрытый показатель бледнеет без зачёркивания;
- легенда «Вовлечённости» скрывает и возвращает соответствующие сегменты без
  сетевого запроса;
- под каждой линией есть лёгкая градиентная заливка до нулевой линии;
- tooltip работает по hover, focus и click; click закрепляет значение;
- шкала никогда не показывает значения ниже нуля;
- подписи оси имеют внутренний запас и не касаются рамки;
- линейчатые карточки не имеют искусственной лишней высоты;
- длинные списки прокручиваются внутри виджета;
- страница не получает горизонтальный overflow;
- иконки действий не имеют постоянного контура и лишнего фона.
- общие селекты команды и периода имеют одинаковую компактную ширину, а кнопка
  обновления примыкает к ним с системным межэлементным отступом;
- легенды двух верхних виджетов Дашборда находятся справа в заголовке карточки;
- названия виджетов используют единый приглушённый стиль и не конкурируют с
  заголовком страницы;
- виджет «По периодам» визуально использует одну составную полосу как
  «Вовлечённость», но не складывает сырые MR, строки и файлы: длина каждого
  сегмента вычисляется после независимой нормализации показателя, а общая длина
  строки нормализуется по максимальной сумме таких безразмерных оценок; справа
  показывается `additions + deletions`, а tooltip содержит точные значения всех
  включённых показателей;
- глобальная CSV-выгрузка находится в шапке, строится локально и учитывает
  текущий фильтр команды; она содержит временные интервалы и строки сотрудников
  со всеми доступными показателями; hover/focus-подсказка явно сообщает про
  учёт выбранной команды;
- сохранённый GitLab token показывается маской; маска является UI-сентинелом и
  никогда не отправляется серверу вместо token;
- правила аналитики сохраняются локально после Enter, blur изменённого числового
  поля или change checkbox; отдельной кнопки сохранения нет;
- стрелки разворачивания используют диагональ «правый верхний — левый нижний»;
  область графика не резервирует лишнюю высоту ниже подписей дат.

## 11. Масштабирование графиков

Все линейные графики используют общий renderer.

- При отношении `max/minPositive < 10` используется линейная шкала от нуля.
- При отношении `>= 10` используется единая нелинейная шкала с подписанными
  реальными значениями.
- Нелинейность применяется только к координате Y; значения, tooltip и суммы не
  преобразуются.
- Сглаживание ограничено диапазоном соседних точек и не уходит ниже нуля.
- X-позиции точек фиксируются равномерно; шрифт не растягивается вместе с SVG.
- Полноэкранный режим ограничен `min(1902px, viewport - 48px)` и
  `min(1080px, viewport - 48px)`.

## 12. Хранение, кэш и безопасность

### Файлы

| Файл | Содержимое | Можно передавать коллегам |
|---|---|---|
| `data/connection.json` | GitLab URL и token | нет |
| `data/routes.json` | команды и usernames | только по разрешённому каналу |
| `data/groups.json` | пути групп | только по разрешённому каналу |
| `data/projects.json` | пути проектов | только по разрешённому каналу |

Запись JSON выполняется атомарно. `data/*.json` не коммитятся.

Правило персонального сигнала (`threshold`, `minimum`) и настройка скрытия
интервалов без активности (`hideInactiveDays`) хранятся отдельно в
browser `localStorage` под ключом `pulse-review-analytics-rule`. Они локальны для
браузерного профиля и не входят в переносимые JSON-файлы команд и источников.

### Memory cache

- Review cache TTL — 15 минут;
- work-volume cache также живёт только до остановки процесса и ограничен TTL;
- изменение источников очищает оба релевантных кэша;
- изменение состава команд обязательно очищает work-volume cache;
- ключ кэша должен включать диапазон и версию конфигурации.

Закрытие Go-процесса останавливает локальный сервер и очищает memory cache, но
не удаляет JSON-настройки.

### Секреты

- token не логируется и не возвращается после сохранения;
- CI запускает `cmd/security-check`;
- браузер получает только признак наличия token;
- URL и пути валидируются до записи;
- сетевые ошибки не должны раскрывать token.

## 13. Ошибки и деградация

- `401`: неверный, истёкший или отозванный token;
- `403`: недостаточно прав или серверная политика;
- `404`: неверный путь либо недоступный приватный объект;
- `429`: ограничение частоты, не отсутствие GraphQL capability;
- `Failed to fetch`: UI открыт не через работающий локальный HTTP-сервер либо
  процесс остановлен;
- неполный diff: данные показываются с признаком неполноты;
- пустые источники: явная ошибка «Не указаны источники GitLab».

Нельзя превращать сетевую ошибку в нулевые метрики. Частично собранные данные
должны быть явно отличимы от полного нуля.

## 14. Тестовая стратегия

### Обязательные локальные проверки

```text
gofmt -l .
go test ./...
go test -race ./...       # macOS
go vet ./...
npm run test:ui
npm run test:browser
go run ./cmd/security-check
```

Если Go отсутствует в среде разработчика, это фиксируется в отчёте; UI-тесты не
считаются заменой backend-тестов.

### Что проверяется на каком уровне

- unit: формулы, даты, buckets, diff parser, fallback, дедупликация;
- HTTP: методы, validation, JSON schema, очистка cache, отсутствие token;
- static UI: обязательные элементы и недопустимые дубли;
- browser: реальные клики, hover/focus, легенды, группировки, сортировка,
  отбор по ФИО, размеры, overflow, переключение вкладок;
- CI: одинаковый результат на macOS и Windows;
- release: CGO выключен, три артефакта — macOS arm64/amd64 и Windows amd64.

### Обязательная матрица группировок

Browser-тест должен для каждого верхнего периода:

1. проверить точный набор доступных группировок;
2. нажать каждую доступную кнопку;
3. проверить формат подписей;
4. проверить изменение количества bucket;
5. проверить сохранение суммы;
6. проверить отсутствие сетевого запроса отдельным счётчиком вызовов `fetch`;
7. выполнить сценарий для всех четырёх метрик и обоих представлений.

Проверка только `aria-pressed` недостаточна: она не доказывает, что данные
действительно перегруппировались.

## 15. Правила внесения изменений

Для каждой доработки разработчик или ИИ обязан:

1. сформулировать затрагиваемый пользовательский сценарий;
2. перечислить изменяемые контракты и инварианты;
3. определить источник данных и атомарную гранулярность;
4. не смешивать получение, расчёт и представление;
5. добавить тест, который до исправления падает по смыслу, а не по строке CSS;
6. проверить macOS/Windows-совместимость launchers и путей, если затронут запуск;
7. обновить продуктовые требования при новом согласованном поведении;
8. создать ADR, если меняется формула, provider, хранение, API или граница слоя;
9. не удалять и не перезаписывать несвязанные пользовательские изменения;
10. не отправлять изменения в remote без явного разрешения владельца проекта.

### Definition of Done

Изменение готово, когда:

- сценарий работает на реальных данных или явно обозначенном mock;
- нет расхождения между общим, командным и персональным итогом;
- локальные визуальные действия не делают GitLab request;
- ошибки и неполнота не маскируются;
- тесты соответствующего уровня проходят;
- документация отражает новый контракт;
- CI macOS и Windows зелёный перед релизом.

## 16. Структура документации, к которой идём

```text
docs/
  PRODUCT_REQUIREMENTS.md       что и зачем делает продукт
  SYSTEM_SPECIFICATION.md       текущее устройство и контракты
  WORK_VOLUME_ARCHITECTURE.md   детальный target design аналитики
  adr/
    0001-go-single-binary.md
    0002-diff-stats-providers.md
    0003-local-persistence.md
    0004-time-bucketing.md
```

ADR создаётся для необратимого или дорогого решения и содержит: контекст,
решение, альтернативы, последствия, миграцию и проверку. Временные визуальные
правки ADR не требуют.

## 17. Известные риски и ближайшие архитектурные задачи

1. Frontend-монолит повышает риск регрессий между вкладками.
2. Граница fallback типизирована, но определение отсутствующей GraphQL
   capability пока зависит от текста ошибки с `diffStatsSummary`.
3. Memory-only diff cache делает повторный запуск дорогим на больших периодах.
4. Атомарный `daily`-ряд увеличивает размер ответа пропорционально длине диапазона
   и числу сотрудников; до постоянного кэша нужно контролировать память и время
   сериализации на годовых диапазонах.
5. Демоданные и production-данные должны быть явно разделены в коде и тестах.
6. Browser test сообщает историческое число проверок вручную; счётчик стоит
   вычислять автоматически.
7. Требуется schema/version для локальных JSON и будущих миграций SQLite.

Приоритет следующего архитектурного этапа: сначала стабилизировать контракт
атомарных временных данных и группировок, затем вводить постоянный кэш, и только
после этого декомпозировать UI без изменения поведения.
